## Cómo se usa

Cada ID identifica una familia de recorridos; no es un issue ni un ticket listo para codificar. Antes de tomarlo: elegir una acción pequeña, confirmar rutas activas/roles/objeto/provincia y service, comparar API existente por consumidor y cerrar campos/errores, identificar pruebas, fixture y todos los casos visuales. Los listados de services/tests del JSON son candidatos; no fueron ejecutados ni equivalen a cobertura.

Cada declaración literal tiene un destino: familia, apoyo/exclusión explícita o pendiente manual. Se incluyen rutas sin template, descargas, AJAX y POST con UI. El número no equivale a pantallas activas. Guardas/autorización heredadas de librerías y rutas generadas por DRF necesitan revisión adicional.

## Cobertura de la asignación

- 770 declaraciones literales finales inspeccionadas sobre 940 archivos de código/configuración leídos como blobs Git, sin importar Django.
- 614 declaraciones asignadas a 95 familias con evidencia; 156 de apoyo/exclusión explícita; 0 declaraciones pendientes de clasificación manual.
- 70 registros DRF y 65 includes preservados como evidencia, sin ejecutar rutas/actions generadas. Las APIs candidatas por familia no están certificadas como equivalentes web.
- Diez rutas dinámicas de importación de Inspecciones y dos de Django auth se registran aparte en el anexo anterior; no se suman como declaraciones nuevas.

## Siguiente validación por familia

1. Resolver cadena URL → vista → service/template y sus acciones, incluidos botones que envían POST a la misma URL.
2. Distinguir consulta, ABM, transición, archivos y generación documental; separar issues pequeños sin duplicar reglas de negocio.
3. Verificar autenticación y permiso real, alcance de datos, errores y consumidores antes de reutilizar API.
4. Definir destino React/legacy/excepción, baseline actual aceptado y manifiesto de cada URL/estado/rol/viewport.
5. Publicar implementación solo con contrato y dependencias cerrados; las familias restantes continúan como requiere descomposición.
