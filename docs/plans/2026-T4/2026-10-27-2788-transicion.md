Depende del [inventario R0](2026-10-27-2786-inventario-estatico.md) y de las

## Límites actuales confirmados

- `src/backends/config/urls.py` monta login/reset antes de includes de usuarios,
  core, dashboard, audittrail, ciudadanos, insumos y encuestas. Los backends
  independientes y stubs se agregan por mecanismos existentes; no reemplazar
  sus registros por un catch-all SPA global.
- `/v2/<module>/...` usa `frontend_v2`, con login obligatorio, allowlist de
  upstreams, GET/HEAD y 503 vacío si el front falla. No reenvía Cookie ni
  Authorization al servidor estático. Mantener esa frontera.
- `src/backends/sisoc_core/usuarios/urls.py` también monta login en `/` y rutas
  propias de cuenta/cambio de contraseña. Conservar orden/aliases hasta definir
  compatibilidad; `/` no puede pasar a inicio por una suposición.
- Orden de middleware: sesión y CSRF/autenticación; acceso web/primer cambio de
  contraseña; confirmación de perfil; encuesta obligatoria; demás controles
  audit/CSP. Sus exenciones incluyen `/api/`; por tanto no basta conservar los
  middleware de HTML para asegurar que nuevas APIs respeten controles forzados.
- `EncuestaObligatoriaMiddleware` redirige a inicio; el modal actual se aporta
  por context processor. Un inicio React sin ese aporte puede bloquear al
  usuario o crear un bypass si solo se replica el menú.
- `/api/users/login/`, logout, me y reset pertenecen a un contrato con tokens y
  consumidores PWA/SIIS; no asumir equivalencia con login de sesión web.

## Recorrido de sesión propuesto

1. Sin sesión, entrar por URL protegida produce login con destino interno
   conservado (path/query y estrategia de hash definida). Entry público y sus
   assets deben poder entregarse sin abrir rutas privadas ni formar un bucle.
2. Antes de autenticar por POST, inicializar CSRF de sesión; conservar protecciones
   actuales contra login CSRF. Django valida credenciales y redirección segura.
3. Con sesión válida, conservar el orden de controles vigente: acceso web,
   contraseña obligatoria, datos personales y encuesta. Estado/remediación se
   consulta al backend; ni ocultar botones ni eximir APIs debe permitir bypass.
4. Tras resolver requisitos, regresar al destino permitido. Si no hay permiso,
   mostrar 403/404 según contrato; no volver al login repetidamente. Validar
   destinos externos, relativos ambiguos, protocol-relative y codificados para
   impedir open redirect. No convertir un POST original en un GET silencioso.
5. Sesión expirada: detener la acción, limpiar datos privados del cache cliente,
   pedir login y conservar destino seguro. Nunca reintentar automáticamente una
   mutación al volver sin saber si se ejecutó. Archivos/formularios sin guardar
   requieren tratamiento explícito, sin guardar secretos/PII en localStorage.
6. Logout invalida sesión Django y datos en memoria; cerrar pestaña o navegar
   atrás no debe recuperar datos privados del cache de React. Considerar varias
   pestañas al definir invalidación, sin agregar coordinación anticipada.

El tratamiento actual del cliente contempla pathname/query, no hash. Debe
decidirse si hash representa estado de navegación relevante y conservarse sin
enviarlo como URL externa o introducir un contrato accidental.

La [propuesta detallada de #2798](2026-10-27-2798-contrato-contexto-web.md)
concreta `@sisoc/sisoc`, `/v2/sisoc/insumos/` y `/api/web/session/` para revisión,
sin crear app ni endpoint. El caso anónimo de Insumos requiere guard específico:
legacy devuelve 403 y v2 genérico redirige al login. El manifiesto lo marca
bloqueado y recomienda conservar 403; no se cambia el login global ni se llama
equivalentes a esas dos pantallas.

## Matriz de pruebas posterior a decisiones

| Caso / experimento | Resultado que se debe demostrar |
|---|---|
| Entrada directa sin sesión y reload de subruta | Login entregable sin bucles, assets públicos solo allowlisted; retorno al destino |
| next interno con query/hash, externo, `//host`, codificación y ruta no permitida | Solo destino interno autorizado, fallback seguro y sin pérdida silenciosa de filtros |
| Cuenta sin acceso web, contraseña pendiente, perfil pendiente y encuesta combinados | Orden actual respetado; APIs y URL directa no saltan restricciones; encuesta se puede responder |
| Credenciales inválidas, reset desconocido, token vencido/usado | Error equivalente a UI actual, sin enumeración de usuarios ni tokens en logs/capturas |
| CSRF ausente/incorrecto y logout por método incorrecto | Rechazo backend, no mutación, sesión y frontend coherentes; 403 CSRF no se oculta como éxito |
| Sesión expira durante lectura, guardado y upload | Mensaje/retorno adecuados, sin datos filtrados, doble guardado ni reintento ciego |
| Usuario cambia ID/objeto/provincia, entra por URL o fuerza request | Acceso denegado por backend aunque UI manipule controles |
| Módulo/ruta desconocido, error 500, permiso 403, timeout/upstream caído | Status correcto, recuperación utilizable; módulos sanos y admin siguen disponibles |
| Assets y app de versiones distintas, versión anterior durante rollback | index no queda fijado a assets inexistentes; frontend previo puede consumir API compatible |
| Enlaces legacy, redirect, export, descarga y formularios POST | Método/query y permisos conservados; no SPA catch-all absorbiendo APIs/media/admin |
| Todas las URLs tocadas y consumidores de shell/estilos | Capturas antes/después/diff y aceptación según plan padre, también móvil/tema/roles |

## Activación, detección y reversión

Por flujo: congelar referencia → contrato compatible → implementar sin activar
por defecto → checks y diff visual → revisión técnica cuando corresponda →
aceptación visual/funcional del responsable → autorización de activación en el
entorno concreto. No se introduce hoy feature flag, setting ni sistema de
rollout nuevo: primero revisar mecanismos existentes y proponer la modificación
mínima si hace falta.

Antes de activar: evidencia de todas las URLs/acciones/roles y enlaces,
monitoreo de 401/403/5xx/503 y redirects en bucle, disponibilidad de estáticos,
rendimiento respecto a baseline y procedimiento de volver a la entrada previa.
Determinar límites medidos por flujo tras el piloto; no inventar presupuesto
de latencia o mejora de rendimiento. No incluir PII en telemetría.

Reversión propuesta: desactivar entrada/enlace React del flujo y restaurar
resolución de la UI Django de la versión compatible conservada; APIs aditivas
siguen funcionando. Mantener assets de la versión previa durante la transición
y comprobar compatibilidad antes de limpiar. No implica revertir tablas,
contraseñas, estados o archivos modificados por usuarios. Si hay cambio de datos,
excede esta migración y necesita su propio plan/decisión.

Retiro de legacy únicamente después de aceptación y ventana de observación
acordada por entorno (sin duración inventada). Primero sacar rutas activas y
observar; eliminar templates/CSS/JS solo tras demostrar que no tienen consumidores
por includes, contribuciones remotas, documentos, admin o apps anteriores.
Un asset compartido no se elimina porque su primera pantalla haya migrado.
Retiro físico y reversión deben ser PRs separados de la primera activación.

Desarrollo, PR integrado, QA, HML y PRD son estados distintos con SHA/resultado
propio. Esta tarea no recomienda merge/deploy ni declara salud de entornos.

## Brechas de transición por consumidor

La [matriz actualizada de flujos](2026-10-27-2786-matriz-flujos.md) y el
[análisis por consumidor](2026-10-27-2786-2788-brechas-por-consumidor.md)
identifican dos decisiones adicionales de alcance concreto: DDJJ PAS por
invitación (#2806) necesita entry público distinto de padrón/descarga protegida;
los requisitos web en APIs de otros runtimes (#2808) no quedan resueltos por
implementar contexto/Insumos dentro del core. La transición de aportes remotos
de Ciudadano 360 a JSON está en #2807; el HTML actual no se incrusta como UI
final React. CDF consulta web frente a API de integración exige #2805. Estos
tickets son de definición y no cambian autenticación, proxy ni permisos.

Las [alternativas de #2808](2026-10-27-2808-alternativas-control-web.md)
concretan G1 (gate en core + constancia firmada por request), G2 (servicio/pool
de política independiente) y G3 (solo core/red privada). G3 no satisface el
negativo fuerte de acceso directo al runtime; un callback G2 al mismo pool del
core en espera del proxy tampoco es una solución de concurrencia. El responsable
eligió G1; ver [registro de decisión](../../registro/decisiones/2026-10-27-2808-control-web-g1.md).
Contrato/operación y comprensión de sus límites siguen pendientes antes de ejecutar.
La propuesta de namespace `/api/web/<dominio>/` también es parte
del detalle por revisar; no se renombraron endpoints existentes ni propuestas
anteriores como si ya hubiera un contrato runtime aceptado.

Actualización de decisiones: PAS P1 conserva sesión restringida;
Ciudadano 360 C2 autoriza `No disponible` ante aporte fallido con excepción visual
acotada. No cambian los demás estados normales. Unfold #2793 e INET #2794 ya

El [paquete del piloto](2026-10-27-2785-paquete-piloto-insumos.md) reúne la
