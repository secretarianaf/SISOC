## Contrato mínimo propuesto de lectura

El dueño sigue siendo `src/backends/sisoc_core/insumos`. Los endpoints nuevos
deben comprobar sesión web, requisitos forzados y `insumos.view_insumo`; la
proyección UI de #2798 no los autoriza por sí sola. El queryset actual no añade
un alcance provincial: no introducirlo ni ampliar reglas por suposición.

| Endpoint propuesto | Datos / semántica |
|---|---|
| `GET /api/web/insumos/` | `count`, `next`, `previous`, `results`; metadata adicional `page`, `page_size`, `num_pages`, `page_range` para reproducir el pager usando `build_compact_page_range` existente |
| `GET /api/web/insumos/options/` | `categorias` con id/nombre de categorías activas en el orden de `get_categorias_queryset`; `sin_categoria_value: "sin"`. Requiere consulta de insumos, no agregar permiso de categorías que la pantalla actual no exige para su select |
| `GET /insumos/<pk>/descargar` | Conservado en Django; mismo archivo, nombre, status, permisos y soporte de inactivos. React no lee media público ni crea endpoint de descarga alternativo |

Cada resultado: id, titulo, categoria_display, fecha_creacion ISO con offset,
creado_por_display, activo y download_url protegida. Cuando la condición actual
de gestión lo permita, edit_url y delete_url conservan las URLs públicas actuales,
con presentación React al activar INS-A bajo M2; en caso
contrario son null. No devolver descripción completa solo porque se usa para
buscar, campos del usuario creador innecesarios ni URL directa del archivo.

Fechas se muestran `d/m/Y H:i` en la zona actual de SISOC; un formateador
compartido se reutiliza solo si produce ese mismo texto, sin sumar segundos u
otro separador. Categoria_display y creado_por_display reutilizan propiedades
actuales del modelo; ausencia de creador se muestra `-`.

Filtro/query del listado:

- `busqueda`: strip y coincidencia actual en título **o** descripción.
- `categoria`: strip; `sin` filtra nulas; valor numérico filtra ID; otro valor
  conserva comportamiento actual sin filtro. Categoría inactiva por URL puede
  filtrar resultados aunque no aparezca en el combo; no corregirlo por asociación.
- `page`: reproducir número y `last` cuando corresponda; páginas inválidas/fuera
  de rango con 404 equivalente. Tamaño fijo 20, sin exponer un tamaño nuevo en UI.
- Orden actual de `get_insumos_queryset`: categoría orden/nombre y fecha
  descendente. No introducir filtro de activo ni desempate que cambie resultados
  sin analizarlo. Fixtures tienen fechas distintas para evitar un baseline con
  empates no deterministas.
- Query repetida conserva semántica de QueryDict.get; URLs de paginación mantienen
  filtros. No usar directamente un `next` de API como destino de navegación HTML.
- Valores numéricos Unicode, enormes y otros bordes se prueban explícitamente;
  si exponen un bug del backend actual, registrarlo y decidir corrección mínima,
  sin presentar una respuesta distinta como paridad verificada.

Metadatos de opciones y lista tienen el mismo permiso de consulta. Categorías
activas en opciones no significan que el listado deba excluir las inactivas.
La extracción mínima de filtros compartidos evita duplicar reglas entre vista
HTML y API; no se reescribe el service completo ni se añade cache.

API con datos: 401 sin sesión, 403 sin permiso o con requisito web pendiente,
404 de página/recurso y errores DRF. La página HTML histórica y el entry React
requieren su comprobación aparte: `/insumos/` anónimo actualmente responde 403,
mientras router v2 genérico redirige a login. Recomendada una comprobación
acotada del entry de Insumos que conserve 403 sin restringir las demás pantallas
de la app `sisoc`. Ese detalle bloquea considerar aprobado el caso anónimo.

## Visibilidad actual frente a autorización

`InsumoListView.get_context_data` calcula `puede_gestionar` con
`user.has_perm("insumos.add_insumo")`. El template usa ese booleano para **Agregar,
Editar y Eliminar**, aunque las rutas de editar/borrar comprueban sus permisos
propios. La categoría tiene otro booleano basado en `add_insumocategoria`.

La migración conserva esa visibilidad y comprueba por separado que un usuario
con alta pero sin change/delete no pueda ejecutar esas acciones. No añadir una
regla «si se muestra el botón, se permite la acción» ni ocultar los botones para
eliminar el caso incómodo. Una mejora de UX sobre esa discrepancia sería otro
pedido con su aceptación, no requisito implícito de migrar.

La descarga no exige que el insumo esté activo. Si el archivo no existe, el
botón sigue teniendo la misma presencia y el destino da 404; no ocultarlo ni
mostrar éxito solo porque el request devolvió una página de error.

## Experimento de aceptación de #2799

1. Preparar solo en entorno sintético autorizado los datos/roles/archivos e
   identificar versión de loader, mappings, reloj, fuentes y navegador.
2. Capturar referencia Django aceptada antes de cambiar UI; ejecutar los casos
   en candidata con idéntica preparación. No usar una captura React como origen
   del expected ni una API simulada como prueba de persistencia.
3. Conservar antes/después/diff y metadatos por caso, incluso con fallo. Comprobar
   que omitir URL o modificar icono/espaciado/texto se detecta, y que repetir el
   mismo caso sin cambios es estable.
4. Verificar el recorrido de consulta/filtro/descarga con API real, además del
   pixel diff y teclado/foco. Estado descarga válido incluye status/headers/bytes,
   no solo un botón visible.
5. El responsable revisa positivos y negativos. Repetir comparación acumulada
   final en la versión integrada y registrar excepciones decididas, sin subir
   cookies, tokens ni datos reales como artefactos.
