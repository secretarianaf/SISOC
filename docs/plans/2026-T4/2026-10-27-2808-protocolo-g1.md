# Protocolo G1: especificación para revisión (#2808)

Fecha: 2026-10-27. Estado: **borrador del agente; G1 elegida, protocolo sin aprobar**.
Deriva de la [decisión G1](../../registro/decisiones/2026-10-27-2808-control-web-g1.md).
No implementa autenticación, middleware, claves, endpoints ni infraestructura.

## Alcance y garantías

Precisión posterior: [S1 elegida para gestión de encuestas](2026-10-27-2788-excepcion-gestion-encuestas.md)
conserva la excepción actual solo al bloqueo de encuesta, por operación/método y
Change efectivo; siguen requisitos superiores y permiso/objeto de cada acción.
No exigir ready universal ni permitir un bypass general por Change. La política
fuente concreta veinte rutas; su mapeo API y validación quedan para implementación.

El core evalúa requisitos web por petición. Para una operación remota permitida
emite una constancia interna firmada, destinada a un runtime y request concretos.
El runtime autentica la sesión actual, verifica constancia y luego aplica permisos,
alcance de objetos y CSRF. No hay callback ni cache de autorización por sesión.

La constancia demuestra una evaluación previa dentro de una ventana acotada;
no autoriza un objeto ni garantiza ausencia de cambios concurrentes de política.
No cifra información, firma el cuerpo ni garantiza uso único. No protege frente
a un runtime comprometido que tenga las mismas claves. Exigir cualquiera de
esas garantías requiere reconsiderar el alcance, no añadir mecanismos ocultos.

Estos experimentos demuestran comportamiento de bibliotecas instaladas, no del
proxy desplegado ni de Gunicorn/NGINX. No se presenta un fallo de producción.

## Petición y datos firmados propuestos

Un único header interno candidato `X-SISOC-Web-Gate`, nunca un header que React
deba obtener o enviar. El core elimina cualquier valor recibido del cliente y
lo sustituye únicamente después de evaluar acceso. Las respuestas hacia cliente,
logs y reportes de errores excluyen la constancia, incluso al fallar el runtime.
El nombre es propuesta nueva, sin cambiar headers actuales en este trabajo.

Payload mínimo propuesto, de tipos estrictos y sin campos desconocidos en v1:

| Campo | Significado y comprobación |
|---|---|
| `v` | Entero de versión, inicialmente 1; rechazar cualquier otra versión |
| `aud` | Nombre del runtime dueño, resuelto desde registro/configuración del servidor; igualdad con identidad local, nunca con un header del cliente |
| `sub` | ID del usuario autenticado representado como string; igualdad con el usuario de la sesión autenticada en destino |
| `session_binding` | Huella criptográfica de la clave de sesión efectiva, calculada mediante primitiva Django con propósito separado; no incluir la cookie ni clave de sesión en texto |
| `method` | Método HTTP exacto en mayúsculas; HEAD y GET no intercambiables |
| `target` | Path y query de la petición HTTP preparada que se enviará; excluye origen/host/fragmento |
| `iat` | Segundo UTC de emisión; validar tipo, futuro permitido y antigüedad según presupuesto acordado |

No transportar permisos, perfil, DNI, estado de encuesta ni listas de centros.
La huella de sesión y el ID siguen siendo datos internos correlacionables:
no registrarlos. No agregar un nonce que sugiera uso único sin mantener estado.
El verificador acota el tamaño del header antes de procesarlo; el límite concreto
se debe contrastar con límites de servidor y tamaño máximo de `target` admitido.

## Firma y frescura propuestas

Reutilizar las primitivas de `django.core.signing` y `django.utils.crypto`
con propósitos distintos para envolvente y binding; sin criptografía propia,
JWT, dependencia nueva ni clave enviada al navegador. Propuesta de propósito
versionado: `sisoc.web-gate.v1` y `sisoc.web-gate.session.v1`.

La envolvente firmada temporal y el `iat` se generan desde el mismo instante.
Además del máximo de antigüedad, comprobar explícitamente que no exceda el futuro
permitido: `max_age` solo no lo demostró en la versión local. Rechazar tipos,
fechas inconsistentes o timestamp ilegible. Verificar firma antes de confiar en
los campos. Comparar bindings mediante la primitiva de comparación constante.

Propuesta de clave: utilizar inicialmente la confianza compartida existente con
propósito separado, sin prometer aislamiento. La política de fallback/rotación
de la envolvente y del binding debe diseñarse como una unidad: aceptar una firma
con clave anterior no basta si se recalcula la huella solo con la nueva.
No habilitar fallback indefinido ni rotar SECRET_KEY como parte de este plan.
Si no existe necesidad de rotación en caliente demostrada, preferir una transición
coordinada del endpoint antes que inventar un gestor nuevo de claves.

Pendientes explícitos antes de código: edad máxima, tolerancia al futuro,
límite de header/URL, política de fallback y procedimiento de retiro de clave.
Se proponen tras observar cola y relojes en entorno aislado autorizado. Los
timeouts de conexión/lectura del proxy no miden espera previa del runtime.

## Cómo vincular la ruta sin reinterpretarla

La firma se calcula sobre el `path_url` de la petición ya preparada para enviar,
no sobre `request.path`, diccionarios de filtros ni la URL anterior a preparación.
Una sola preparación debe determinar lo firmado y lo enviado; no preparar una
copia para firmar y dejar que otra llamada reconstruya el destino después.
Conservar proxy streaming, cookies, redirects desactivados, timeouts y tratamiento
de fallos; cualquier adopción de `PreparedRequest` debe verificar también esos
contratos y configuración de transporte, sin añadir requests duplicados.

El receptor necesita el request-target crudo observado por el servidor confiable.
La fuente candidata de WSGI/ASGI debe comprobarse en la composición real; no se
dio por existente `RAW_URI`/`REQUEST_URI` ni se aceptará un header del cliente
como sustituto. Exigir forma relativa al origen, sin fragmento ni caracteres
de control, y comparación inequívoca con `target`. No ordenar parámetros, pasar
query por dict ni decodificar repetidamente. Cualquier normalización admisible
debe quedar especificada y probada con ambos extremos, incluyendo rewrites.

**Bloqueo de habilitación:** sin fuente confiable o ante representación ambigua,
no ejecutar negocio y no activar la nueva ruta en ese entorno. No reconstruir
silenciosamente desde un path ya decodificado. Rutas codificadas, separadores,
Unicode, duplicados y parámetros vacíos requieren pruebas de ida y recepción.
Este punto está pendiente: las pruebas de preparación no acreditan recepción.

## Flujo propuesto y ubicación

1. Core autentica y compone los mismos requisitos del
   [contexto web](2026-10-27-2798-contrato-contexto-web.md): acceso web, contraseña,
   perfil y encuesta. Reutiliza servicios de sus dueños, sin imports a verticales.
2. Si falla un requisito, responde JSON y no hace request de negocio al runtime.
   Si falla la evaluación, nunca asume `ready`.
3. Si se modificó/rotó la sesión, persistir y comprobar que la cookie realmente
   reenviada identifica la misma sesión que se firmará. No emitir una constancia
   para sesión nueva reenviando cookie vieja. Determinar tratamiento concreto
   antes de habilitar; no cambiar login/cookies globalmente para ocultarlo.
4. Resolver dueño, preparar transporte y emitir constancia solo para la nueva API
   protegida. Los helpers de aportes/consultas internas que llamen esa API también
   deben atravesar esta comprobación; no basta instrumentar un único proxy view.
5. Runtime autentica sesión y valida constancia al inicio, antes de leer/parsear
   cuerpo para negocio. Validar CSRF antes de una mutación; no consumir por firma
   un multipart completo ni convertir el proxy en dueño de autorización de objetos.
6. Runtime ejecuta permiso/alcance/transacción actuales. No reintenta mutaciones
   al vencer constancia, fallar red o volver del login.

La composición de política pertenece al core; helpers mecánicos de verificación
pueden pertenecer al kernel. La integración exacta middleware/permission debe
revisar orden de autenticación y parseo DRF antes de elegir ubicación. En modo
local/monolito el core evalúa directamente; jamás confiar en header externo
para simular evaluación local. No crear registro de políticas duplicado ni
importar usuarios/encuestas desde kernel o runtime.

## Rutas y errores propuestos

La [matriz de remediaciones](2026-10-27-2798-contratos-y-remediaciones.md)
precisa el tratamiento de cambio obligatorio, perfil y respuesta de encuesta.
No exigir ready a esas operaciones porque bloquearía la resolución del requisito;
no eximirlas de los requisitos prioritarios anteriores. Para negocio se exige
ready. La constancia solo acredita la evaluación para su target/método, no un
permiso reusable para llamar cualquier otra operación. En core local se evalúa
directamente; no se inventa un callback por introducir estas excepciones.

Conservar la propuesta de nuevas APIs `/api/web/<dominio>/` y el endpoint
`/api/web/session/` como introspección accesible con sesión aunque existan
requisitos pendientes. Namespace y exenciones exactas siguen por revisar.
Login/reset/PAS público necesitan su contrato propio; no eximir todo `/api/web/`.
PWA, `/api/vat/web/`, admin, media y assets `/v2/` conservan sus contratos.

| Situación | Respuesta propuesta para nuevas APIs de negocio |
|---|---|
| Sesión ausente/inactiva | 401 JSON explícito, sin datos privados ni redirección; probar el status real de DRF |
| Requisito web pendiente en core | 403 JSON con estado prioritario ya definido en contexto; cliente consulta contexto para remediar |
| Constancia ausente, alterada, vencida, futura o incongruente | 403 JSON genérico, sin revelar campos/firma ni ejecutar negocio |
| Entorno incapaz de comprobar target o contrato de verificación mal configurado | No habilitar ruta; si falla en ejecución, error de servicio 503 mediante manejo revisado, sin fail-open |
| Fallo al evaluar política/DB | Error por manejo existente sin declarar ready; no convertir indisponibilidad en permiso denegado o menú vacío |
| CSRF/permiso/objeto inválido | Mantener contrato del dueño; no esconder diferencias legacy de 403/404 ni reintentar |
| Transporte al runtime falla tras envío | Mantener incertidumbre de la mutación y 503/504 del proxy; nunca afirmar que no hubo escritura |

Proponer códigos estructurados específicos solo en el contrato público revisado;
no cambiar el cliente global para interpretar cualquier 403 como login.
Respuestas privadas sin cache compartida. Métricas/logs solo causa agregada,
runtime y versión, sin constancia, cookie, binding, usuario ni URL/query con datos.

## Compatibilidad, pruebas pendientes y habilitación

La ruta nueva no se publica hasta que receptor verifique v1 y productor la emita.
Desplegar soporte sin activar rutas, verificar compatibilidad y después habilitar
el piloto; no se ha ejecutado esa secuencia ni creado otro feature flag.
Para revertir, desactivar la nueva entrada y volver al flujo legacy autorizado;
no aceptar requests sin firma como compatibilidad transitoria.

| Evidencia posterior | Qué impide aceptar un falso positivo |
|---|---|
| Firma/versión, audiencia, usuario, sesión, método y target alterados individualmente | Cada rechazo comprueba cero ejecución del servicio de negocio |
| Cookie válida sin header y header falsificado desde cliente | Directo al runtime rechaza; core reemplaza el header, no lo concatena |
| Reloj pasado/futuro, frontera exacta, vencimiento, cola, rotación | Repetir con Django objetivo; no usar solo mocks como prueba de presupuesto real |
| URL preparada recibida por servidor real aislado | Duplicados, vacíos, Unicode, `%2F`, `%25`, `%7e`, `+`, `%20`, `?` vacío, rewrites y prefijos; demostrar fuente cruda confiable |
| Multipart, HEAD, cuerpo grande, error y respuesta upstream | Verificador previo a parseo; transporte y CSRF conservados; nada privado en errores |
| Cambio/rotación de sesión y cambio concurrente de permisos | No ligar sesión vieja; dominio revalida permisos propios; límites temporales explícitos |
| Core, runtime aislado y monolito | Sin callback, sin import entre servicios y sin bypass local vía headers |
| PWA/API key/token, PAS público, admin #2789 | Contratos existentes intactos; no inferirlo de tests nuevos de G1 |
| Bloqueos y recuperación en pantalla | Incorporar URL/estado al manifiesto visual; diseño idéntico, diff y aceptación humana posteriores |

No cerrar #2808 con estos experimentos: faltan revisión del protocolo,
parámetros operativos, verificación de recepción, pruebas de servicios y control
de comprensión previo a ejecutar arquitectura. La elección G1 no se reabre.

Validación realizada en esta fase: introspección y experimentos sintéticos locales
descritos arriba, más revisión de rutas documentales. Sin suite de aplicación,
HTTP, DB, Docker, servidor, build, capturas, CI, commits ni despliegue.
Se publicó y comprobó un resumen de avance en #2808 y #2785, ambos abiertos;
este documento continúa local sin commit/push.
