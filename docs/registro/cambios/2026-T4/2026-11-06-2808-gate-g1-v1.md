# Cambio: gate G1 v1 para APIs web remotas de verticales (#2808, #2785)

## Alcance

Se integra el mecanismo común del
[protocolo G1 v1](../../decisiones/2026-11-06-2808-protocolo-g1-v1.md), opción A
con ventana de 60 s. No se publica ninguna API real de vertical: ningún
`url_prefixes` de `src/backends/config/backends.json` cambia.

- `src/backends/kernel/core/web_gate.py`: firma y verificación de la constancia
  `X-SISOC-Web-Gate`, respuestas JSON, `WebGateMiddleware` y `WebGatePermission`.
- `src/backends/kernel/core/backend_proxy.py`: vista del core para
  `/api/web/<vertical>/`, read timeout de 60 s solo en ese prefijo, 414/503/504 JSON,
  `X-Request-Id` saneado y corrección de la sesión rotada.
- `src/backends/config/settings.py`: registra `core.web_gate.WebGateMiddleware`
  después de `AuthenticationMiddleware` y define `SISOC_WEB_ACCESS_POLICY`.
- Tests: `src/backends/kernel/tests/test_web_gate.py` (nuevo) y
  `src/backends/kernel/tests/test_backend_proxy.py`.

## Comportamiento

- Un vertical publica sus APIs web agregando `api/web/<vertical>/` a sus
  `url_prefixes`. Otro nombre bajo `api/web/` hace fallar el arranque del proxy.
- En esas rutas el core responde 401 JSON sin sesión y 403 JSON con `state` si hay
  un requisito web pendiente, sin reenviar. Si el usuario está listo, firma y
  reenvía. El runtime rechaza con 403 JSON genérico cualquier constancia ausente,
  alterada, vencida (más de 60 s), futura (más de 2 s) o incongruente, antes de
  ejecutar la vista.
- El header `X-SISOC-Web-Gate` que mande un cliente se descarta en todos los
  procesos y nunca se reenvía.
- Rutas proxied existentes: mismos timeouts (5 s y 25 s), mismos textos de error y
  mismo `X-Request-Id`.
- Corrección previa a G1, que aplica a todas las rutas proxied: si la autenticación
  del core rota la clave de sesión (por ejemplo, al validar con
  `SECRET_KEY_FALLBACKS` durante una rotación de clave), el backend recibe la clave
  vigente y el navegador recibe su `Set-Cookie`. Antes recibía la clave vieja, que
  ya no existía, y el usuario quedaba deslogueado.
- Monolito: no hay salto remoto; la permission evalúa la política local y el header
  se ignora.

## Verificación

Entorno local aislado: imagen fijada
`sha256:a8e59c769a921d84cf449d17b9bd173bd72c367d376d3e604d95ff2c0abe9502`, sin red
externa, datos y claves sintéticos.

- RED: el test de sesión rotada falló sobre la base (la cookie del cliente seguía
  con la clave vieja); `test_web_gate.py` no importaba (`core.web_gate` no existía).
- GREEN: `test_web_gate.py` y `test_backend_proxy.py` pasan. También pasan las
  suites de proxy, servicios de backends, API key, SIIS, sesión web, runtimes,
  middleware CSP, PAS y `kernel/core/tests`, y `-k registro_de_urls_al_dia`.
- `black --check`, `pylint` 10/10 en los archivos tocados y
  `makemigrations --check --dry-run` sin cambios.
- HTTP real entre dos contenedores con gunicorn (core y runtime PAS):
  - targets codificados: la firma coincide con `RAW_URI` en todos los reenviados;
    `..`, prefijos parecidos o en mayúsculas no ejecutan negocio;
  - alteraciones de versión, audiencia, usuario, sesión, método, path, query, orden
    de query, edad de 61 s, futuro de 5 s, firma, clave ajena, campo extra, header
    duplicado y header de 7000 bytes: 403 sin negocio; 9000 bytes: 431 de gunicorn;
    58 s: aceptado;
  - HEAD y OPTIONS se firman con su método; CSRF del dueño intacto;
  - runtime caído: 503 JSON; con gunicorn a 120 s, una respuesta de más de 60 s da
    504 JSON (`uncertain: true` en POST) y el negocio corre una sola vez;
  - rotación de clave con fallback en core y runtime: la sesión sobrevive en
    `/api/web/pas/` y en una ruta proxied existente; sobre la base, la misma ruta
    borra la cookie del cliente;
  - diferencial de 16 rutas existentes con la base: respuestas idénticas.

No se probaron Nginx, PWA, otros verticales ni carga realista. Con el timeout por
defecto de gunicorn (30 s), un request de 40 s terminó en 500 HTML: ver el límite en
la decisión.
