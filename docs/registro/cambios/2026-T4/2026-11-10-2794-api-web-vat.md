# Cambio: la API de INET React pasa a `/api/web/vat/` con G1 v1 (#2794, #2785)

## Alcance

La API de sesión que consume INET React (`/v2/inet/`) se publicaba en `/api/inet/`, fuera
del protocolo común de las APIs web de verticales. Se muda completa a `/api/web/vat/`, el
namespace G1 v1 del vertical VAT
(`docs/registro/decisiones/2026-11-06-2808-protocolo-g1-v1.md`), **sin alias**: `/api/inet/`
deja de existir en el proxy del core, en el runtime de VAT y en el monolito.

Contrato y mapeo de las 63 rutas: `docs/plans/2026-T4/2026-11-10-2785-vat-api-web-m2.md`.

- `src/backends/config/backends.json`: el prefijo `api/inet/` de `vat` se reemplaza por
  `api/web/vat/`. El core lo atiende con la vista G1 del proxy.
- `src/backends/vat/VAT/web_api_urls.py` (antes `api_inet_urls.py`, namespace
  `vat_web_api`) se monta en `src/backends/vat/vat_runtime/urls.py`.
- `src/backends/vat/VAT/api_inet_views.py`: `InetAPIView` usa
  `[WebGatePermission, IsAuthenticated]`. `InetSchema` descarta las tres partes del montaje
  para que los `operationId` sigan siendo `inet_<recurso>_<método>`.
- `src/backends/config/urls_inet_v2.py` genera el contrato sobre `api/web/vat/`;
  `openapi.inet.yaml` e `inet.generated.ts` se regeneraron y solo cambian los paths.
- Front: `inetClient` usa `/api/web/vat/`; el proxy de Vite y el mock de
  `src/frontends/e2e/inet.e2e.ts` también. Las pantallas no cambian.
- Escritores: los mismos ModelForms y services de VAT que usan las vistas legacy.
- `src/backends/config/url_registry.json` regenerado con `generar_registro_urls`.

## Cambio de comportamiento

**Usuarios con requisitos web pendientes ahora reciben 403 en INET.** Antes `/api/inet/` solo
exigía sesión y permisos de VAT. Ahora, como en toda API `/api/web/<vertical>/`, el core
evalúa `SISOC_WEB_ACCESS_POLICY` antes de reenviar:

| Situación | Antes (`/api/inet/`) | Ahora (`/api/web/vat/`) |
|---|---|---|
| Sin sesión | 401 | 401 `{"detail": "Inicie sesión para continuar."}` |
| Sin acceso web en el perfil | la API no lo evaluaba | 403 `state: web_access_denied` |
| Cambio de contraseña obligatorio | la API no lo evaluaba | 403 `state: password_change_required`, `required_action_url: /password/first-change/` |
| Confirmación de perfil pendiente | la API no lo evaluaba | 403 `state: profile_confirmation_required`, `required_action_url: /mi-cuenta/confirmar/` |
| Encuesta obligatoria pendiente | la API no lo evaluaba | 403 `state: mandatory_survey_required`, `required_action_url: /inicio/` |
| Requisitos al día | según permisos VAT | igual que antes |

INET muestra el `detail` del 403 («Debe completar el requisito de acceso web.») y todavía no
redirige a `required_action_url`; queda como entrega VAT-API02 del contrato.

Las respuestas llevan `Cache-Control: private, no-store` y `Vary: Cookie`. Un request al
runtime sin constancia válida del core responde 403 `{"detail": "Solicitud no autorizada."}`
sin ejecutar negocio. CSRF, permisos de acción y alcance por CFP siguen igual.

## Despliegue

Core, runtime VAT y `front_inet` deben salir en el mismo despliegue: un front anterior
llama a `/api/inet/` y recibe 404. No se dejó alias por pedido explícito.
